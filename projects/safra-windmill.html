Draft · Safra WindMill: operating Python ETL jobs

Safra · Draft · 2019–2020

DRAFT — pending author review. Reconstructed from the records below; sources and review points remain visible in this version.

A working script was only part of the job

In Safra’s Analytics and Data Visualization area, Python scripts processed data before it reached APIs and reporting interfaces. Getting a transformation to work was one challenge. Operating it was another: knowing what was running, checking the outcome and investigating a failure without relying on the person who wrote the script.

I developed Safra WindMill in that setting, as a tool for managing Python ETL jobs. A Tech Talk I presented in July 2020 captures its practical purpose: giving the people running those workloads more autonomy.

Section sources: [w1], [w2], [r].

Making the execution model explicit

The design separated four concepts: the virtual environment, the project, the job and an individual run. Virtual environments isolated libraries and dependencies. Projects grouped scripts and inputs. Jobs represented work that could be started, stopped or scheduled. Runs stored the status, timestamps and logs of a particular execution.

That distinction made it possible to treat processing as work with a history, rather than a series of isolated commands. It also separated a project’s dependency requirements from those of other projects.

Section sources: [w2].

Letting people run their code

The recorded requirements included Python support, integration with the DevOps delivery pipeline and the ability to run a job without extending the scheduler itself. Another requirement was to capture normal program output: debugging prints should appear in the logs without modifying the job’s source code.

These requirements kept the tool focused on operating existing ETL projects. Users needed to bring their code, schedule it and inspect what happened. The presentation also lists NoSQL storage as a requirement; that is not enough evidence to identify a production database in this draft.

Section sources: [w1].

Discovering a related approach along the way

I started building the scheduler before I knew Apache Airflow. During development, I discovered that it addressed a similar family of problems. WindMill became a reference to that discovery.

The work involved more than implementing execution logic. It meant defining a tool around the way the area developed ETLs, managed environments and operated daily workloads. The Tech Talk created a place to explain those choices and share the tool inside the bank.

Section sources: [r], [w1].

What the records support

The records support my role as the developer and show a tool presented with requirements, an execution model and a practical demonstration. They support an account of job management and execution visibility, but do not establish adoption figures or measured operational savings.

The next review should clarify how job dependencies were represented and which features remained in active use. This draft does not claim feature parity with Airflow, high availability or a measured processing-time improvement.

Section sources: [r], [w1], [w2].
