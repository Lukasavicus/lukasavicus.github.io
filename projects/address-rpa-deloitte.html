Address-resolution RPA

Deloitte · 2018

The problem surfaced in collections, but started at registration

A customer could reach Claro through a store, a kiosk or another sales channel. Somewhere along the way, someone had to enter their details. An incomplete, inconsistent or incorrect address could remain unnoticed until it interfered with billing and collection.

Our Deloitte team was working with Claro’s business teams when we identified this manual process. We proposed treating the existing customer records and preparing a routine to repeat the treatment over time.

The concern was revenue collection. Problematic addresses made it harder to collect amounts owed, with the issue estimated at around R$1 million per month.

Before the rules came questions about the data

I worked on a Claro computer with access to the Oracle database. In that setting I was not using my own machine or a VPN to access the data. I began by exploring a large sample, writing queries and looking for recurring patterns.

The investigation was exploratory: examine records, form a hypothesis, write a rule and check how many cases it helped resolve. Rather than starting with a similarity algorithm, I started with simpler differences in representation and components entered in the wrong fields.

There were unnecessary spaces, abbreviated street types and titles, and entire addresses entered on one line. A street field could also contain a building number, unit or neighbourhood. Abbreviating Rua as R. does not necessarily make an address invalid; standardisation helped compare different representations before deciding what needed correction.

Small functions, in an order that mattered

I used Python and pandas. I organised the treatment as small functions: one cleaned spaces, another expanded street types, another handled titles. A separate function assembled the hierarchy and ran the treatments in the specified order.

That composed function was what I passed to apply on the DataFrame column. Functions were first-class values: they could be stored in a sequence, received by another function and used to build a new behaviour.

Order was part of the solution. The text needed a predictable shape before the street type and its title could be handled in context. Replacing letters or abbreviations indiscriminately could introduce a new problem instead of resolving the original one.

Present-day reconstruction — not the client’s code.

def compose_rules(rules: Iterable[Rule]) -> Callable[[object], str | None]:
    ordered_rules = tuple(rules)

    def normalize(value: object) -> str | None:
        if value is None or value is pd.NA:
            return None
        if not isinstance(value, str):
            if pd.api.types.is_scalar(value) and bool(pd.isna(value)):
                return None
            raise TypeError("The street field must be text or a missing value")
        result = unicodedata.normalize("NFKC", value)
        for rule in ordered_rules:
            result = rule(result)
        return result or None

    return normalize


normalize_street = compose_rules((clean_spaces, expand_street_type, expand_title))
frame = pd.DataFrame({
    "street_original": ["  R.   Dr. Exemplo  ", "Av. Prof. Modelo"]
})
frame["street_normalized"] = frame["street_original"].apply(normalize_street)

See the example expansion functions
def expand_street_type(value: str) -> str:
    # Expand only at the beginning of a street field, never every R or AV.
    value = re.sub(r"^R\b\.?\s+", "Rua ", value, flags=re.IGNORECASE)
    return re.sub(r"^AV\b\.?\s+", "Avenida ", value, flags=re.IGNORECASE)


def expand_title(value: str) -> str:
    # Context matters: this example handles a title after a recognised type.
    titles = {"dr": "Doutor", "prof": "Professor", "cap": "Capitão"}
    return re.sub(
        r"^(Rua|Avenida)\s+(Dr|Prof|Cap)\b\.?\s+",
        lambda m: f"{m.group(1)} {titles[m.group(2).lower()]} ",
        value,
        flags=re.IGNORECASE,
    )

An external reference, beyond the text itself

The Correios address database, including postal codes and other address information, was our reference. Alongside the street name, I checked consistency with neighbourhood, city and state. That narrowed the candidates worth comparing.

I also used regular expressions to identify components mixed into the street field. The intention was to organise what had been entered before looking for a match. Normalising text and validating an address were different steps.

The Correios reference changed too, with updates obtained through a contracted service. This was another reason to prepare more than a one-off cleanup: later runs needed to work against an updated reference.

Knowing when to ask a person

Levenshtein distance appeared in a later step. After the earlier treatments and geographic filtering, it helped compare the text with candidate addresses.

A single candidate meeting the criteria could be assigned by the rule. If two or three candidates remained acceptable, the case went to a human agent. A spreadsheet presented the alternatives so the person could inspect the options rather than begin the search from scratch.

Similarity helped select candidates; the number of acceptable matches determined whether a case could proceed automatically or needed human review.

Resolving an address and applying it were different jobs

I developed the data analysis, resolution rules and monitoring dashboard, using Python/pandas, Oracle access through ODBC and Qlik for visualisation.

We could not update the client database directly. Another team member implemented the RPA integration that took the results and applied corrections through the application interface. That integration also populated the spreadsheet of alternatives for human review.

The separation mattered: the engine produced a proposed treatment, an agent handled ambiguous cases and the RPA applied changes in the system. My work and my colleague’s work complemented each other; I did not author the entire automation.

The initial treatment and the handover

The initial treatment achieved approximately 86% case resolution. The ordered rules handled much of the work, while ambiguous cases were routed to human review.

I left the process prepared for recurring execution and transferred the knowledge to the stakeholder responsible for continuing the operation.

The delivery combined the initial cleanup with preparation for continued operation: organised rules, exception review, integration with the application and dashboard monitoring.

What I can reconstruct today

The original code remained with the client. The example in this article was written now, with fictional data, to show how I would organise that idea today. It is not recovered code, a copy of Claro’s implementation or a complete reproduction of the historical rules.

The executable example covers function composition and application to a column while preserving the input. It does not access the Correios reference, validate where a customer lives or write to any system. Geographic matching, similarity, human review and RPA are part of the project workflow and are outside the scope of this small example.

To me, the work shows how data exploration becomes an operable process: understand the patterns, organise rules that can be explained, recognise cases that require judgement and prepare someone else to continue the operation. The knowledge transfer was part of that delivery.
